Where Driftnet stands.

Detection results

Measured on four days of one machine's traffic.

The test data is the public Stratosphere CTU-Normal captures (23, 24, 25 and 20): one Windows machine's normal use over four days. Everything below uses the default configuration, with an alert budget of 10 a day. Last run 10 October 2026.

BASELINE

Two days, 6.7 hours

44,466 flows. Web traffic (tcp/443, tcp/80) had enough data for its own models; everything else shared a pooled one.

NORMAL TRAFFIC, UNSEEN

Two more days, 4.7 hours: 1 alert

48,019 flows. One alert, severity LOW, for unusual packet sizes on a single flow. One large download was muted, as the default configuration does.

Read these numbers with care

They show the detector behaves sensibly on a small test. They do not show how it does on your network.

  • The attack flows are synthetic, built to look like what the capture library reports for such traffic. They are not captures of real tools.
  • One machine and 6.7 hours is a small baseline. Rare contexts, meaning anything that is not web traffic on that machine, had too little data to alert. That is why the two tunnels were missed.
  • Low-and-slow traffic that looks like ordinary browsing is out of reach for flow statistics. Catching beacons needs timing analysis across flows, which Driftnet does not do.
  • Something that is rare is not necessarily malicious, and the reverse.
Development

What works, what is unverified, what is not built.

Version 0.2.0 replaced the first prototype's lab-trained model with a baseline fitted to the network it runs on.

Working in 0.2.0

Implemented and under test.

  • Baseline from your own traffic: record, fit, inspect, and re-fit from flows the daemon has kept
  • Flow and host layers, each service scored against its own kind
  • Alert budget in place of a score threshold
  • Incidents: repeats counted, kinds muted, an hourly cap
  • New-service detection
  • Inputs: live interface, pcap, Zeek conn.log, Suricata eve.json
  • IDS awareness: skips or tags connections Suricata or Snort 3 already alerted on
  • Outputs: text log, JSON lines, webhook
  • Offline replay of a capture or log through the daemon's own code
  • Explanations: each alert says how rare the event is and which measurements made it so
Built, not yet verified

The code exists. It has not been exercised.

  • Live interface capture. Same code path as pcap replay, but the test environment had no capture privileges
  • Windows, through Npcap. Not run on this version
  • Raspberry Pi, 64-bit. Supported by the dependencies, not yet run on a device
  • Wazuh. The example rules have not been tested against a live Wazuh
  • Real attack tools. Every attack so far is synthetic
  • More than one network. One machine's traffic so far
Not built

Open today.

  • Beacon and tunnel detection. Needs timing analysis across flows
  • Licence. None has been published, so the code is not open source today
  • Container image or a one-command install
  • Dashboard. Alerts are files and webhooks; there is no web interface
  • Hosted console
Timeline

How it got here.

  1. December 2025

    The idea

    A two-page paper in the IEEE HiPC 2025 workshop proceedings: put an anomaly model behind a signature engine and score what it leaves unflagged.

  2. June 2026

    First prototype

    An autoencoder trained on a lab dataset, scoring live flows. It did not transfer: on real traffic it flagged almost everything.

  3. October 2026

    Detector rewritten, v0.2.0

    Baselines fitted to your own traffic, an alert budget, flow and host layers, Suricata and Zeek input, explanations on every alert, and a test suite.

  4. November 2026

    Early access opens

    The self-hosted daemon, for people on the list to run on their own networks. Join the list

Want to run it on your network?

Early access opens November 2026. One machine's traffic is a small test; more networks are what this needs next.
